Первый вопрос для твоей роли:
В GitHub Actions jobs выполняются на self-hosted runners в Kubernetes. Разработчики жалуются: pipeline раньше занимал 15 минут, теперь — 50.
Как ты определишь, jobs долго ждут свободного runner или сами build/test стали выполняться медленнее? Что посмотришь первым?
Ответь как на интервью, своими словами.




Ты рассуждаешь правильно: сначала сравнить время ожидания job, затем длительность её выполнения и отдельных шагов. Уточнение: ожидание runner видно в состоянии job, а не обязательно в её обычных логах — выполнение ещё не началось.
Как посмотреть в GitHub:
Открой Repository → Actions → нужный workflow run → нужную job. Для выполнявшейся job посмотри длительность шагов: checkout, установка зависимостей, build, tests, upload artifacts. Сравни с предыдущим быстрым запуском того же workflow. Так найдёшь, какой именно шаг замедлился. GitHub Docs
Если job ожидает runner, проверь сообщение об ожидании и требуемый runs-on в YAML. Затем открой Settings → Actions → Runners: есть ли подходящие runners, доступны ли они или заняты. Важно наличие подходящего runner: GitHub учитывает labels/groups, а не просто любой свободный runner. GitHub Docs
Команды GitHub CLI — запускаются в каталоге репозитория, при установленном и авторизованном gh:
# Последние запуски — здесь находишь RUN_ID
gh run list --limit 10

# Сведения о запуске и его jobs
gh run view RUN_ID

# Открыть запуск в браузере
gh run view RUN_ID --web

# Логи конкретной job
gh run view --job JOB_ID --log

RUN_ID — идентификатор запуска workflow, JOB_ID — отдельной job внутри него. Это разные идентификаторы. Take GitHub to the command line
На интервью твой ответ можно сформулировать так:
«Сначала разделю задержку на ожидание runner и выполнение job. Сравню длительности jobs и шагов с предыдущим нормальным запуском. Если задержка до старта — проверю доступность подходящих runners и их масштабирование. Если после старта — найду замедлившийся шаг и проверю его логи, ресурсы и кеш».

Продолжаем сценарий: выяснили, что job ждёт runner 35 минут, а сам build по-прежнему занимает 15 минут. 
Runner pods находятся в Kubernetes в состоянии Pending. Какие команды ты выполнишь и что будешь искать?


Если поды на офтендинг, это значит, что-то мешает им сделать деплой. Может быть лейбл не тот, нод, и может быть не хватает памяти в нод. Может не хватает места. Что-то мешает им сделать деплой.Какие команды, но, скорее всего, я буду делать команды Kubernetes pod describe, logs и смотреть, там уже ошибки и от них уже исходить.
Направление правильное: проверяешь, что мешает runner pod запуститься, и начинаешь с describe.

Уточнение: Pending не всегда означает, что pod не назначен на node. Он может уже быть назначен, но ждать скачивания образа или подготовки volumes.

Начни так — ci-runners здесь пример namespace:

kubectl get pods -n ci-runners -o wide
kubectl describe pod RUNNER_POD -n ci-runners

Смотри колонку NODE, затем Events внизу describe.

Что видно	Что проверять
FailedScheduling: Insufficient memory/cpu	Requests pod и доступную для планирования ёмкость nodes
untolerated taint	Taints nodes и tolerations pod
didn't match Pod's node affinity/selector	nodeSelector, affinity и labels nodes
unbound ... PersistentVolumeClaims	PVC и предоставление диска
ErrImagePull / ImagePullBackOff	Образ, доступ к registry, сеть

kubectl logs полезен, когда контейнер уже запускался. Если scheduler ещё не назначил pod на node, логов приложения нет — главная информация в Events.
Про «место» уточняй: свободная RAM, CPU, место на диске или число доступных pod slots — это разные причины.


Все эти сообщения объясняют, что мешает pod запуститься, но относятся к разным этапам.
1. Insufficient memory/cpu — не хватает ресурсов для размещения
В pod задаются requests:
resources:
  requests:
    cpu: "2"
    memory: "4Gi"

Это означает: scheduler должен найти node, где можно выделить 2 CPU и 4 GiB памяти по requests.
Он учитывает allocatable node и requests уже размещённых pods. Даже если сейчас фактическое потребление маленькое, запрошенная ёмкость уже занята для планирования.
Проверка:
kubectl describe node NODE_NAME

Смотри Allocatable и Allocated resources. kubectl top показывает фактическое потребление — это другой показатель.
2. untolerated taint — node ограничивает размещение pods
Taint ставится на node, например:
dedicated=ci:NoSchedule

Это означает: новые pods без подходящего разрешения сюда не размещать.
Toleration задаётся в pod:
tolerations:
  - key: dedicated
    operator: Equal
    value: ci
    effect: NoSchedule

Она позволяет pod пройти это ограничение. Она не заставляет pod выбрать эту node и не отменяет проверку ресурсов.
Используют, например, чтобы обычные приложения не попадали на nodes для CI.
3. nodeSelector / affinity — pod требует определённые nodes
На node есть labels:
workload: ci

Pod может потребовать такую метку:
nodeSelector:
  workload: ci

Если подходящих nodes нет, pod не разместится.
nodeSelector — простой обязательный выбор по labels. nodeAffinity позволяет задавать более сложные правила: обязательные условия или предпочтения.
Проверить labels:
kubectl get nodes --show-labels

Запомни разницу: taint ограничивает вход на node, selector/affinity задаёт выбор со стороны pod.
4. unbound PersistentVolumeClaims — запрос на хранилище ещё не обеспечен
PVC — объект Kubernetes, которым приложение запрашивает хранилище, например диск на 20 GiB.
Запрос должен связаться с PV, представляющим предоставленное хранилище. Часто диск создаётся автоматически через StorageClass и CSI-драйвер.
Если это не получилось, pod может ждать. Причины: неправильный StorageClass, ошибка создания диска, неподходящая зона или отсутствие подходящего PV.
kubectl get pvc -n ci-runners
kubectl describe pvc PVC_NAME -n ci-runners

Смотри состояние и Events. Pending у PVC иногда является нормальным ожиданием выбора node при WaitForFirstConsumer; важна конкретная причина в Events.
5. ErrImagePull / ImagePullBackOff — не получается скачать образ
Pod уже может быть назначен на node, но контейнеру нужен образ из registry:
image: registry.example.com/runner:1.0

Возможные причины:
- Неверное имя образа или tag.
- Нет прав на private registry.
- Проблема сети или DNS.
- Registry недоступен.
ErrImagePull сообщает об ошибке скачивания. ImagePullBackOff означает, что Kubernetes делает паузы между повторными попытками.
kubectl describe pod RUNNER_POD -n ci-runners

В Events ищи конкретное сообщение: например, unauthorized, not found или timeout.
Для всех пяти случаев первая команда — describe pod, а дальше проверяешь именно тот ресурс, на который указывает ошибка.





Про scheduler ты ответил правильно: он учитывает requests.memory pod и уже запрошенную память на node относительно её allocatable, а не текущее потребление из kubectl top.
Karpenter — контроллер, который создаёт новые worker nodes, когда pods не помещаются на существующих. В AWS он запускает подходящие EC2 instances. Когда новая node зарегистрируется и станет готова, scheduler сможет разместить там pod. Amazon EKS
Для диагностики тебе нужно понимать три объекта:
Объект	Для чего нужен
NodePool	Правила выбора nodes: допустимые типы, зоны, Spot/On-Demand, taints и общий лимит ресурсов
EC2NodeClass	Настройки AWS: образ ОС, IAM role node, subnets, security groups, диски
NodeClaim	Запрос Karpenter на конкретную новую node; показывает этапы её создания


Это объекты Kubernetes, поэтому их смотрят через kubectl. Karpenter
Если новая node не появляется, проверяем по порядку.
1. Сам Karpenter работает?
kubectl get pods -A -l app.kubernetes.io/name=karpenter

Из вывода узнаёшь namespace и имя pod. Затем:
kubectl logs KARPENTER_POD -n KARPENTER_NAMESPACE --since=15m

Ищешь сообщения о проблемном pod, несовместимых требованиях или ошибках AWS.
2. Настройки разрешают создать подходящую node?
kubectl get nodepools
kubectl describe nodepool NODEPOOL_NAME

kubectl get ec2nodeclasses
kubectl describe ec2nodeclass NODECLASS_NAME

Проверяешь Conditions/Events и ограничения:
- Не достигнут ли общий NodePool.spec.limits.
- Разрешены ли instances с достаточной памятью.
- Совместимы ли правила NodePool с selector/affinity и tolerations pod.
- Готов ли EC2NodeClass: найдены ли необходимые AWS ресурсы. Karpenter
3. Karpenter уже пытался создать node?
kubectl get nodeclaims
kubectl describe nodeclaim NODECLAIM_NAME

Conditions помогают отличить: instance не запустился, node не зарегистрировалась в Kubernetes или не стала готова. Дальше проверяешь указанную причину: IAM permissions, AWS quotas, доступность EC2 capacity, сеть или bootstrap node. Karpenter

Вопрос: если build запускает восемь тестовых процессов параллельно, что проверишь, чтобы понять, почему закончилась память?


Да, логи процессов и память хоста нужно проверить. Но логи обычно не показывают, сколько памяти потреблял каждый процесс, поэтому нужны ещё метрики.
Я бы разделил проверку:
- Лимит контейнера: сколько памяти разрешено всему ci-runner.
- Потребление процессов: сколько одновременно потребляют восемь тестовых процессов и сам build.
- Память хоста: не закончилась ли RAM у всей машины.
Например: контейнеру выделено 4 GiB, а каждый из восьми процессов потребляет около 700 MiB. Вместе это уже примерно 5,5 GiB, без остальных процессов. Контейнер может получить OOM, даже если на хосте ещё есть свободная память.
Практическая проверка гипотезы: повторить тот же build с меньшей параллельностью и измерять память. Если с двумя процессами он проходит, а с восемью превышает лимит, это подтверждает связь с параллельностью. Само по себе это ещё не доказывает утечку.
На интервью можно сказать:
«Проверю лимит контейнера, пиковое потребление и число параллельных процессов. Сопоставлю с памятью хоста и повторю запуск с меньшей параллельностью под мониторингом».
